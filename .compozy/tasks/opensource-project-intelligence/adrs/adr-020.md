# ADR-020: Stream Job Updates With SSE and Retain Polling

## Status

Accepted

## Date

2026-08-21

## Context

Collection, recalculation, analysis, crawling, export, and purge are durable asynchronous Jobs. The
UI must show factual progress through transient network failures and process restarts without making
real-time transport the source of truth.

## Decision

Expose resumable Server-Sent Events for Job updates. Every event contains the complete current Job
representation and an event ID. Browsers reconnect with `Last-Event-ID`. The ordinary Job GET route
remains the authoritative polling fallback and communicates cadence through `Retry-After`. Do not
ship WebSockets.

## Alternatives Considered

### Alternative 1: Polling only

- **Description**: Fetch the Job resource periodically.
- **Pros**: Smallest protocol surface and simple recovery.
- **Cons**: Adds latency and repeated requests during active work.
- **Why rejected**: The selected experience requires pushed progress while keeping polling fallback.

### Alternative 2: WebSockets

- **Description**: Use a bidirectional persistent channel.
- **Pros**: Supports arbitrary real-time interaction.
- **Cons**: Adds connection state and capabilities not needed for one-way Job updates.
- **Why rejected**: SSE matches the event direction with a smaller contract.

## Consequences

### Positive

- Active progress reaches the browser promptly.
- Polling and durable Job state preserve correctness when streaming is unavailable.

### Negative

- API and deployment proxy must support long-lived HTTP responses and reconnection.
- The Job surface has two read transports to verify.

### Risks

- Events may be missed or repeated; clients replace local state with the complete representation.

## Implementation Notes

The terminal event closes the stream. Alerts do not inherit a streaming contract from this decision.
