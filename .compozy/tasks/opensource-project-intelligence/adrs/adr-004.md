# ADR-004: Use One Shared Workspace With Fixed Product Roles

## Status

Accepted

## Date

2026-08-20

## Context

ADR-001 requires application-managed authentication and authorization but intentionally leaves the
workspace and role model open. The product must support multiple people collaborating on one tracked
technology portfolio. It needs enough separation to protect integrations, policies, and destructive
actions without requiring users to design a custom permission system before they can use it.

## Decision

The product will provide one shared workspace containing all users, projects, repositories,
policies, analyses, and alerts. Every authenticated user will have exactly one of three fixed roles:

- `Admin` manages users, source credentials and integrations, policy definitions and versions, and
  destructive lifecycle actions.
- `Analyst` registers and edits projects and repositories, requests synchronization and analysis,
  runs queries and comparisons, configures alerts, and selects an existing policy for an evaluation.
- `Viewer` reads dashboards, comparisons, recommendations, evidence, and exports without changing
  product state.

Admins author and version policies. Analysts may select an existing policy but may not create or
modify one. The product will not provide user-defined roles or permission sets in this delivery.

## Alternatives Considered

### Alternative 1: Admin and Member

- **Description**: Separate administration from all other product use with only two roles.
- **Pros**: Smaller authorization matrix and simpler user administration.
- **Cons**: Cannot grant read-only access without also granting catalog and analysis mutations.
- **Why rejected**: The selected three-role model protects shared state while supporting observers.

### Alternative 2: Custom Roles and Permissions

- **Description**: Allow administrators to construct roles from individual permissions.
- **Pros**: Maximum flexibility for organizations with specialized responsibilities.
- **Cons**: Adds permission-authoring, validation, migration, and support complexity without a
  demonstrated product need.
- **Why rejected**: Fixed roles cover the identified personas with a more predictable contract.

## Consequences

### Positive

- Every product action has an unambiguous minimum role.
- Read-only stakeholders can use the intelligence without being able to mutate shared data.
- Policy governance remains separated from applying an approved policy.

### Negative

- Teams cannot isolate separate portfolios inside the same installation.
- Organizations with different job functions must map them onto three product roles.
- Adding multi-workspace tenancy later will require an explicit new product and data boundary.

### Risks

- Permissions can drift between HTTP and UI surfaces; the technical contract must define one
  authorization matrix and test enforcement at the backend boundary.
- A single workspace may reveal all tracked projects to every Viewer; deployment guidance must state
  that the workspace is one visibility boundary.

## Implementation Notes

Stage 2 will select the authentication and session mechanisms, define initial Admin bootstrap, and
map every public operation to one of these roles. Those technical choices must not introduce custom
roles or additional workspaces implicitly.
