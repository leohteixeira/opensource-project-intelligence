# ADR-017: Gate Workspace Intelligence Behind Approval While Exposing a Public Catalog Teaser

## Status

Accepted

## Date

2026-08-20

## Context

The VPS deployment should let people discover the product and register normally, but the product has
one shared workspace. Granting every new internet identity immediate access would expose the full
portfolio and let untrusted accounts consume queries and exports. Hiding the product completely
before approval would make public discovery and onboarding unnecessarily opaque.

## Decision

Anonymous visitors may view a limited catalog containing Project names, public descriptions, and
public source links. Metrics, health, analyses, comparisons, radar, alert history, exports, and user
information require approved workspace membership.

People register and authenticate through the shared Keycloak. A newly authenticated identity enters
a pending-access state and cannot view protected intelligence until a local Admin approves it and
assigns one fixed product role. The pending user sees a clear status and can sign out; repeated
login does not bypass approval.

The public deployment will enforce registration and application rate limits, query and export
quotas, global collection/AI/crawling limits, and administrative suspension. These controls protect
the installation and do not define paid plans or billing.

## Alternatives Considered

### Alternative 1: Immediate Viewer Access

- **Description**: Every verified identity enters the shared workspace as Viewer.
- **Pros**: Lowest onboarding friction.
- **Cons**: Any internet user can consume protected intelligence and resource-intensive features.
- **Why rejected**: The user selected Admin approval before workspace access.

### Alternative 2: No Anonymous Product Surface

- **Description**: Show nothing beyond sign-in until membership is approved.
- **Pros**: Strongest visibility boundary.
- **Cons**: Visitors cannot discover which projects the public-facing service covers.
- **Why rejected**: The selected direction exposes a limited public catalog.

## Consequences

### Positive

- Visitors can understand the catalog before requesting access.
- Admins retain control over the one shared workspace and resource consumption.
- Protected intelligence and user data never become anonymous surfaces.

### Negative

- Admins must process access requests.
- Public and protected representations of a Project must remain explicitly separated.

### Risks

- A public endpoint could accidentally include derived intelligence; its contract must use an
  intentionally limited representation rather than filter a protected response opportunistically.
- Registration abuse can still burden the shared identity system; global Keycloak protections remain
  an external dependency.

## Implementation Notes

Stage 2 will define the public catalog contract, pending membership lifecycle, approval transitions,
quota/status surfaces, and coordination requirements for global Keycloak registration controls.
