# ADR-018: Use Same-Origin Browser Sessions and Keycloak Bearer Tokens

## Status

Accepted

## Date

2026-08-21

## Context

The public VPS serves a React browser application and a versioned HTTP API. Authentication belongs
to workspace-shared Keycloak, while this product owns local approval, fixed roles, scopes,
suspension, and authorization. Human and automated clients need access without exposing browser
tokens to JavaScript or creating product-owned credentials.

## Decision

Browser users authenticate through OIDC Authorization Code Flow with PKCE and receive a same-origin,
Secure, HttpOnly product session cookie. Non-browser clients use Keycloak bearer tokens. Every token
subject must resolve to an approved local member or service account. Service accounts can receive
Viewer or Analyst roles plus a restricted scope subset, never Admin. Local authorization remains
authoritative for both modes.

## Alternatives Considered

### Alternative 1: Browser sessions only

- **Description**: Do not expose authenticated automation.
- **Pros**: Small authentication surface.
- **Cons**: Prevents supported API integrations and service automation.
- **Why rejected**: The HTTP API is a deliberate external automation surface.

### Alternative 2: Bearer tokens only

- **Description**: Let the browser retain and send OIDC tokens.
- **Pros**: One authentication mechanism.
- **Cons**: Expands token exposure and complicates safe browser renewal and revocation.
- **Why rejected**: A server-held browser session provides the safer public-VPS default.

## Consequences

### Positive

- Browser credentials remain inaccessible to application JavaScript.
- Automation uses standards-based identities without product API keys.
- Local approval, suspension, roles, scopes, and audit apply consistently.

### Negative

- The product must support two request-authentication modes.
- Service accounts require external Keycloak provisioning and local binding.

### Risks

- Incorrect audience or issuer validation could accept unintended tokens; validation must fail
  closed.
- A broad service-account scope could bypass human workflows; Admins must assign least privilege.

## Implementation Notes

The API contract is frozen in `_dx.md`. Shared realm, client, mail, MFA, and recovery configuration
remain external to this repository.
