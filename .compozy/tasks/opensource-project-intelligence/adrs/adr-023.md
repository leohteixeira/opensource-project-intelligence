# ADR-023: Use Conditional HTTP and Cursor APIs With Numbered Browser Pages

## Status

Accepted

## Date

2026-08-21

## Context

The public workspace has concurrently changing shared resources and large collections. API clients
need deterministic retries and stable traversal, while browser users expect visible page position.

## Decision

Require `ETag`/`If-Match` for shared-resource mutations and `Idempotency-Key` for creates/actions.
Use opaque cursor pagination in the API. The browser stores the cursor chain for the current query
and presents numbered previous/current/next pages, resetting that chain when filters change.

## Alternatives Considered

### Alternative 1: Last-write-wins and page/size

- **Description**: Accept concurrent overwrites and use numeric offsets.
- **Pros**: Familiar and smaller HTTP contract.
- **Cons**: Hides stale edits and produces unstable pages during ingestion.
- **Why rejected**: Shared governance and live ingestion require explicit conflict behavior.

### Alternative 2: Body versions and dual API pagination

- **Description**: Put versions in JSON and expose both cursors and numeric pages.
- **Pros**: Avoids conditional headers and supports arbitrary page jumps.
- **Cons**: Duplicates semantics and weakens one canonical traversal contract.
- **Why rejected**: Standard conditional HTTP and one cursor API are clearer.

## Consequences

### Positive

- Retries do not duplicate work and stale writes do not silently win.
- API traversal remains stable while browser users retain recognizable page navigation.

### Negative

- Clients must retain ETags, generate idempotency keys, and store cursor history.
- Browser page numbers are session/query-relative and do not permit arbitrary jumps.

### Risks

- Missing conditional headers could become inconsistent across routes; shared contract tests must
  enumerate every mutation.

## Implementation Notes

The API default page size is 50 and maximum is 200. Cursors are opaque and query-bound.
