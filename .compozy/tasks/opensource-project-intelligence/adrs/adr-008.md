# ADR-008: Resolve Cross-Source Project Identity Automatically and Reversibly

## Status

Accepted

## Date

2026-08-20

## Context

The complete product combines repositories, packages, documentation, websites, changelogs, and feeds
from multiple providers. Requiring users to link every source manually creates substantial catalog
maintenance, while keeping one Project per source fragments intelligence about the same technology.
Automatic identity resolution can reduce that work but may also conflate similarly named or related
projects.

## Decision

The product will automatically associate source records with an existing Project by evaluating
names, verified URLs, package metadata, repository metadata, declared relationships, and similarity
signals. Every automatic association will retain its source evidence, resolution method, confidence,
and decision version.

Analysts can inspect, correct, split, or reassign an automatic association after it is created.
Corrections are audited and retained as identity constraints so that later synchronization or
reprocessing does not silently recreate a rejected association. Project and Repository remain
separate canonical concepts as required by ADR-005.

## Alternatives Considered

### Alternative 1: Analyst-Confirmed Association

- **Description**: Suggest likely relationships but require a user to confirm every association.
- **Pros**: Minimizes false automatic merges.
- **Cons**: Creates a manual bottleneck as projects gain sources and packages.
- **Why rejected**: The selected behavior explicitly allows automatic association with later
  correction.

### Alternative 2: One Project Per Source

- **Description**: Never combine records across providers.
- **Pros**: No entity-resolution errors.
- **Cons**: Fragments metrics, adoption signals, releases, and evidence for the same technology.
- **Why rejected**: It prevents the multi-source intelligence layer required by the product.

## Consequences

### Positive

- Projects can gain comprehensive source coverage without exhaustive manual linkage.
- Every association remains explainable and correctable.
- Retained corrections improve later resolution without erasing original provenance.

### Negative

- Entity resolution becomes a product capability with confidence, review, correction, and audit
  requirements.
- Incorrect associations can temporarily contaminate aggregated metrics and analyses.

### Risks

- Fuzzy similarity can join unrelated projects; the product must expose associations and their
  evidence prominently enough for Analysts to review.
- A correction may invalidate downstream intelligence; Stage 2 must define recalculation and stale
  result behavior.

## Implementation Notes

Stage 2 will define deterministic identifiers, match features, confidence thresholds, correction
constraints, and downstream invalidation. Vendor identifiers must never replace canonical Project or
Repository identity.
