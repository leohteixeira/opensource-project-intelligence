# ADR-033: Use PostgreSQL Hybrid Retrieval and Deterministic Topic Candidates

## Status

Accepted

## Date

2026-08-21

## Context

Documentation RAG and issue intelligence must recover exact identifiers and semantic matches, keep
Project/time/source filters, preserve evidence, and accept analyst corrections. Vector-only search
misses exact technical tokens; LLM-only grouping cannot be reproduced.

## Decision

Use PostgreSQL full-text search and `pgvector` similarity, filtered by Project, source, language,
time, and evidence type. Combine ranked lexical and semantic candidates with versioned Reciprocal
Rank Fusion. An optional reranker may reorder candidates but cannot make basic retrieval
unavailable. Each chunk points to immutable source evidence and records parser, chunker, embedding,
and index versions.

Build topic candidates from a mutual-k-nearest-neighbor embedding graph with versioned distance and
connectivity thresholds. Deterministic connected components form candidate clusters. An LLM may name
and summarize a cluster but cannot determine membership. Analyst split, merge, relabel, and
item-move corrections persist as constraints and apply to later recomputation.

## Alternatives Considered

### Alternative 1: Vector-only retrieval and clustering

- **Description**: Use nearest embeddings for both search and topic membership.
- **Pros**: One ranking signal.
- **Cons**: Weak exact-token behavior and unstable implicit clustering boundaries.
- **Why rejected**: Technical evidence needs lexical recall and explicit grouping rules.

### Alternative 2: External search or Python ML service

- **Description**: Add a dedicated search cluster or clustering runtime.
- **Pros**: Broader algorithms and scaling options.
- **Cons**: Adds operational and cross-runtime complexity before measured need.
- **Why rejected**: PostgreSQL already owns structured filters, FTS, and vectors at expected scale.

## Consequences

### Positive

- Exact and semantic retrieval share transactional filters and provenance.
- Topic membership is reproducible and corrections survive reprocessing.

### Negative

- PostgreSQL carries vector indexing and hybrid ranking load.
- Graph thresholds need evaluation datasets and versioning.

### Risks

- Approximate indexes can reduce recall; offline evaluation compares exact and indexed results.
- Corrections can conflict; constraint validation rejects impossible overlapping decisions.

## Implementation Notes

Object storage retains source documents; PostgreSQL retains normalized text chunks required for FTS,
embeddings, offsets, digests, and evidence links. Never embed secrets or private content.
