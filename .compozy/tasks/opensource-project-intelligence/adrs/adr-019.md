# ADR-019: Expose Snowflake Resource IDs as Decimal Strings

## Status

Accepted

## Date

2026-08-21

## Context

Resources need stable identifiers across the API, Jobs, evidence links, audit events, and exports.
The browser uses JavaScript, whose numeric representation cannot safely carry every 64-bit integer.

## Decision

Use Snowflake IDs for persisted resources and serialize every ID as a decimal string in JSON and as
a decimal path segment in URLs. Clients treat the value as opaque and do not derive time, ordering,
authorization, or resource type from its layout.

## Alternatives Considered

### Alternative 1: Type-prefixed opaque IDs

- **Description**: Encode an opaque suffix behind prefixes such as `prj_` or `job_`.
- **Pros**: Resource type is recognizable in logs.
- **Cons**: Adds a second application encoding around the selected identifier.
- **Why rejected**: The selected public identity is the Snowflake decimal value itself.

### Alternative 2: UUIDs

- **Description**: Use standard UUID strings.
- **Pros**: Widely supported and decentralized.
- **Cons**: Does not satisfy the selected Snowflake contract.
- **Why rejected**: The surface decision explicitly selected Snowflake IDs.

## Consequences

### Positive

- IDs are compact, sortable at the persistence boundary, and globally unique under configured nodes.
- String serialization avoids JavaScript precision loss.

### Negative

- Resource type is not visible from an ID alone.
- Generation requires coordinated epoch, node identity, and clock behavior.

### Risks

- Clock regression or duplicate node IDs can collide; Part II must define fail-closed generation.
- Clients may assume chronological order; the contract explicitly forbids that dependency.

## Implementation Notes

Snowflake generation details are an internal-design decision. Public schemas declare IDs as strings
with a decimal-digit constraint.
