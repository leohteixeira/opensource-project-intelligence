# ADR-010: Preserve Versioned, Immutable AI Analysis Runs

## Status

Accepted

## Date

2026-08-20

## Context

Release analysis, issue classification, clustering, summaries, trend explanations, comparisons, RAG,
and natural-language analytics may produce probabilistic results. Replacing or directly editing
those results would erase the relationship between an output, its evidence, and the model and prompt
that produced it. The product also needs feedback suitable for evaluation without presenting human
edits as model output.

## Decision

Every AI analysis execution will create an immutable, versioned run containing its structured
output, source evidence, provider and model identity, prompt version, execution time, and terminal
status. Reprocessing creates a new version and never overwrites the earlier run.

Analysts may flag a result as inaccurate, attach feedback, request a rerun, and choose which version
is currently presented. They may not silently edit generated content. Human feedback and visibility
selection remain separate, attributed records.

## Alternatives Considered

### Alternative 1: Keep Only the Latest Result

- **Description**: Replace prior analysis whenever reprocessing succeeds.
- **Pros**: Simpler storage and presentation.
- **Cons**: Destroys reproducibility, audit history, and before-after evaluation data.
- **Why rejected**: It conflicts with evidence-backed, versioned probabilistic behavior.

### Alternative 2: Allow Direct Editing

- **Description**: Let Analysts modify generated classifications and narrative in place.
- **Pros**: Users can immediately correct visible mistakes.
- **Cons**: Makes it impossible to distinguish model output from human-authored content.
- **Why rejected**: Feedback and visibility controls provide correction without falsifying
  provenance.

## Consequences

### Positive

- Every displayed analysis can be reproduced and evaluated against its exact inputs.
- Human corrections become attributable evaluation evidence.
- Provider or prompt upgrades can be compared without erasing history.

### Negative

- Storage and interfaces must support multiple runs and an explicit presented version.
- Sensitive or incorrect historical output requires a separate access or deletion policy rather than
  in-place editing.

### Risks

- Users may confuse a selected version with the newest version; the interface must display both
  selection and execution metadata.
- Evidence changes can make a previously selected run stale; stale analyses must be labeled and must
  not masquerade as current.

## Implementation Notes

Stage 2 will define schemas, status transitions, prompt identity, evidence references, visibility
selection, stale detection, feedback records, and evaluation exports.
