# ADR-035: Verify With Real Boundaries and Publish Repository Specifications Before Code

## Status

Accepted; requires repository ADR updates before implementation

## Date

2026-08-21

## Context

The complete product depends on PostgreSQL semantics, NATS delivery, object storage, Valkey,
provider protocols, browser accessibility, concurrent workers, generated contracts, and AI
evaluations. Unit-only testing would miss the highest-risk boundaries. The workflow bundle also
lives under `.compozy`, while repository rules require versioned specifications next to code.

## Decision

Keep Go unit tests table-driven with standard `testing`, hand-written port fakes, fuzz cases for
parsers and policy/metric inputs, and race detection. Use Testcontainers for isolated PostgreSQL,
NATS, Valkey, and S3-compatible integration fixtures. Provider adapters use deterministic HTTP and
Git fixture servers. Contract checks regenerate OpenAPI and `sqlc` outputs and fail on diff.

Use Vitest, Testing Library, and MSW for web components; Playwright drives public and protected
browser journeys, mobile layouts, locale routes, keyboard paths, and automated `axe` checks. Manual
WCAG review remains required for semantics automation cannot establish. AI evaluation datasets cover
fidelity, citations, classification, retrieval, clustering, tool selection, and refusal behavior.

The `.compozy` bundle remains the workflow source. The first implementation task publishes the
approved product, architecture, data, API, event, AI, metric, evaluation, observability, security,
and deployment specifications under the numbered `specs/` structure. It also creates repository ADRs
superseding foundation-phase decisions for `sqlc`, frontend libraries, Google ADK, data services,
and messaging before their code lands.

## Alternatives Considered

### Alternative 1: Shared Compose fixtures only

- **Description**: Reuse one long-lived integration environment for all suites.
- **Pros**: Faster local startup after warm-up.
- **Cons**: Cross-test state and ordering reduce reproducibility.
- **Why rejected**: High-risk data and concurrency tests need isolated ownership.

### Alternative 2: Keep specifications only in `.compozy`

- **Description**: Treat task artifacts as permanent repository documentation.
- **Pros**: No publication step.
- **Cons**: Violates the repository's numbered specification contract and weakens code proximity.
- **Why rejected**: Workflow artifacts and accepted repository specifications have different roles.

## Consequences

### Positive

- Tests exercise the semantics most likely to fail in production.
- Accepted architecture becomes durable and reviewable beside the code.

### Negative

- Integration and browser suites require Docker and take longer than unit suites.
- Specification publication is a blocking implementation task.

### Risks

- Container tests can become slow or flaky; pin images, use readiness probes, isolate networks, and
  retain failure logs without secrets.
- Documentation can drift after publication; tasks update the numbered specification and contract in
  the same change as behavior.

## Implementation Notes

The repository ADR for testing supersedes only the shared-Compose integration-fixture clause of
ADR 0004. Standard-library Go testing and race requirements remain unchanged.
