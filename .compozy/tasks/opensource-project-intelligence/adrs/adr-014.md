# ADR-014: Provide a Closed, Versioned Metric Catalog With Comparable Time Windows

## Status

Accepted

## Date

2026-08-20

## Context

The complete product requires more than the seven initial metrics: it must support Activity,
Community, Maintenance, Concentration, Stability, Security, and Adoption dimensions. Allowing users
to write arbitrary formulas would undermine reproducibility and dramatically expand validation,
while retaining only the initial metrics would leave later intelligence unsupported. Comparisons
also become misleading when projects use different observation windows or missing data is converted
to zero.

## Decision

The product will ship a closed, product-owned, versioned catalog containing the seven initial
metrics and the metrics required for all selected health dimensions. Each metric definition will
expose its formula, version, unit, observation window, eligibility and coverage rules, and
missing-data behavior. Users cannot define arbitrary metric formulas in this delivery.

Metrics and comparisons support preset windows of 30, 90, 180, and 365 days plus a custom interval
bounded by available coverage. Every project in one comparison uses the same observation window and
cutoff. Coverage gaps remain explicit and never become numeric zero.

## Alternatives Considered

### Alternative 1: Keep Only the Seven Initial Metrics

- **Description**: Reuse the narrow initial metric set for all later product capabilities.
- **Pros**: Smallest calculation and testing surface.
- **Cons**: Cannot substantiate the complete health, security, stability, and adoption vision.
- **Why rejected**: It would make advanced product conclusions depend on incomplete evidence.

### Alternative 2: User-Defined Metric Builder

- **Description**: Let Admins author formulas and aggregations.
- **Pros**: Organizations can encode specialized indicators.
- **Cons**: Weakens cross-project comparability and adds a programmable calculation surface with
  significant safety and migration complexity.
- **Why rejected**: Versioned product metrics and configurable adoption policies provide the needed
  flexibility at safer boundaries.

## Consequences

### Positive

- Metric results remain reproducible and testable across projects and time.
- Health, comparisons, trends, and policies can reference stable metric versions.
- Users can answer custom temporal questions without comparing mismatched windows.

### Negative

- Adding or changing a metric requires a product release and versioned recalculation behavior.
- Some custom organizational signals cannot be represented as metrics and must instead be expressed
  in policy configuration.

### Risks

- A large catalog could imply every metric is available for every source; coverage and applicability
  must remain first-class.
- Formula upgrades can change historical interpretation; results must retain the metric versions
  used at calculation time.

## Implementation Notes

Stage 2 will enumerate exact definitions, aggregation levels, source prerequisites, snapshot rules,
version transitions, and custom-window validation.
