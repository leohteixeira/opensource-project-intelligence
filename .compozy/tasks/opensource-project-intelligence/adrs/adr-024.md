# ADR-024: Keep Credential Mutation Outside the Product Surface

## Status

Accepted; supersedes the credential-management clause of ADR-004

## Date

2026-08-21

## Context

The product runs on a public VPS and consumes source and model credentials managed by its Operator.
ADR-004 originally assigned source credential management to Admins, while later product decisions
placed secret lifecycle outside the application. The surface also needed a decision on whether to
ship a dedicated operator CLI.

## Decision

The VPS Operator configures non-secret environment values and injects source, Keycloak, session, and
model secrets through the deployment platform. The product has no credential mutation API and no
dedicated CLI. Admins receive a redacted operations UI/API for capability, health, quota, aggregate
usage, cost, and non-secret configuration status. No secret value or reversible representation is
returned.

## Alternatives Considered

### Alternative 1: Dedicated operator CLI

- **Description**: Ship an `opi` command for migrations, status, Jobs, providers, and diagnostics.
- **Pros**: Consolidates operational workflows.
- **Cons**: Adds a separately versioned surface that duplicates deployment and HTTP capabilities.
- **Why rejected**: Environment configuration, health routes, migration scripts, and redacted HTTP
  status satisfy the selected operating model.

### Alternative 2: Admin-managed credentials

- **Description**: Store and mutate source/model credentials through the product UI/API.
- **Pros**: Centralizes application setup.
- **Cons**: Expands secret storage, authorization, audit, and exposure risk inside a public product.
- **Why rejected**: Secret lifecycle is explicitly owned by the VPS Operator.

## Consequences

### Positive

- Product responses, UI, exports, audit, and telemetry never need to expose secret values.
- The shared deployment retains one clear secret-management boundary.

### Negative

- Credential changes require deployment access rather than an Admin product workflow.
- Operators use existing deployment/migration surfaces instead of one product CLI.

### Risks

- Admin status could imply a credential is valid when only presence is known; status must
  distinguish configured, authenticated/probed, degraded, and unavailable signals.

## Implementation Notes

ADR-004 remains authoritative for workspace roles except its source-credential assignment.
