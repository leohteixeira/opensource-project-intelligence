# ADR-026: Use PostgreSQL, S3 Storage, NATS JetStream, and Valkey With Explicit Ownership

## Status

Accepted

## Date

2026-08-21

## Context

The complete product preserves canonical facts, selected raw payloads, documents, exports, vector
indexes, durable work, and transient acceleration state. PostgreSQL alone would keep operations
simple but would make large immutable content expensive. Using several infrastructure services
without strict ownership would create competing sources of truth.

## Decision

PostgreSQL 18 with `pgvector` is the transactional system of record. It stores domain state,
memberships, jobs, checkpoints, metric snapshots, provenance, object hashes and references,
transactional outbox entries, AI run metadata, audit records, full-text indexes, and embeddings.

S3-compatible object storage holds compressed raw payloads, crawled documents, page snapshots, large
diffs, and generated export artifacts. Keys are content-addressed beneath a Project prefix;
PostgreSQL records ownership, media type, size, digest, retention state, and provenance.

NATS JetStream delivers durable asynchronous commands at least once. PostgreSQL remains the
authoritative Job lifecycle and the transactional outbox is the only publisher. Workers use durable
pull consumers, explicit acknowledgements, bounded batches, and idempotent handlers.

Valkey is non-authoritative and disposable. It may hold bounded caches, rate-limit counters,
short-lived deduplication keys, and ephemeral SSE fanout. A Valkey loss may reduce performance or
live updates but cannot lose Jobs, permissions, evidence, or analytical results.

## Alternatives Considered

### Alternative 1: PostgreSQL only

- **Description**: Store every payload, document, export, queue, and cache in PostgreSQL.
- **Pros**: One service to operate and back up.
- **Cons**: Couples large immutable objects and transient load to the transactional database.
- **Why rejected**: The complete scope includes document crawling, evidence packages, diffs, and
  RAG.

### Alternative 2: Valkey Streams as the broker

- **Description**: Use the already selected Valkey service for durable consumer groups.
- **Pros**: Removes NATS from the deployment.
- **Cons**: Makes a disposable cache responsible for durable delivery and complicates recovery
  truth.
- **Why rejected**: The selected ownership model intentionally keeps Valkey non-authoritative.

## Consequences

### Positive

- Each data class has one explicit owner and recovery path.
- Large content does not inflate transactional tables or backups.
- Worker delivery can scale independently while Job state stays queryable and auditable.

### Negative

- Local and VPS deployments operate four data services.
- Cross-service cleanup is asynchronous and requires reconciliation.

### Risks

- An outbox publisher defect can stall work; backlog age and publish failures require alerts.
- Object deletion can partially fail; deletion uses a resumable purge rather than optimistic
  removal.

## Implementation Notes

Start NATS JetStream and Valkey as single-node services with persistent NATS storage in the VPS
profile. Keep cluster-ready configuration without claiming single-VPS high availability. Use an
outbox identifier as the JetStream message deduplication identifier. Never place credentials or raw
payloads in messages, cache keys, logs, or telemetry.
