# ADR-030: Combine Provider APIs With Restricted Git Mirrors and Hardened Crawling

## Status

Accepted

## Date

2026-08-21

## Context

The product needs code-host metadata, commit topology, branches, diffs, documentation, registries,
and future providers without allowing vendor types or user-controlled URLs into the domain. API-only
commit ingestion is quota-heavy and provider-specific. Git and crawling introduce command, SSRF,
redirect, DNS-rebinding, decompression, and resource-exhaustion risks.

## Decision

Create one adapter per source/provider. Use an official or mature SDK when it materially improves
pagination, authentication, or rate-limit handling; immediately map its DTOs to canonical input
types. Shared HTTP transport supplies deadlines, retries, quota observation, redaction, and OTel.

Use official code-host APIs for social and administrative metadata. Use the native `git` executable
inside a restricted worker for ephemeral or cacheable bare mirrors that provide commit topology,
default-branch history, branch activity, and bounded diff metadata. Mirrors are reconstructible
caches, never canonical storage.

Outbound collection accepts only allowed schemes and explicit Project associations. It resolves DNS
and rejects loopback, private, link-local, multicast, metadata, and disallowed ports before every
request and redirect. It revalidates redirects, bounds bytes, decompression ratio, MIME types,
depth, duration, redirects, and concurrent requests. Local Git is disabled by default in production
and can access only operator-allowlisted roots.

## Alternatives Considered

### Alternative 1: Provider APIs only

- **Description**: Read commits and diffs exclusively through REST or GraphQL.
- **Pros**: No Git subprocess or mirror cache.
- **Cons**: Higher quota consumption and inconsistent topology support across providers.
- **Why rejected**: Full history and multi-provider comparison benefit from native Git semantics.

### Alternative 2: Build a generic connector framework first

- **Description**: Normalize every possible provider through one configurable runtime.
- **Pros**: Broad theoretical extensibility.
- **Cons**: Creates an extension platform before concrete adapters establish stable commonality.
- **Why rejected**: Small consumer-declared ports are sufficient and safer.

## Consequences

### Positive

- Canonical models remain provider-neutral.
- Commit ingestion uses one mature protocol and reduces code-host API pressure.
- URL and Git inputs have explicit fail-closed limits.

### Negative

- Worker images include native Git and a restricted mirror volume.
- Each provider still needs mapping, pagination, quota, and fixture coverage.

### Risks

- Provider schema drift can silently reduce coverage; contract fixtures and coverage diagnostics
  detect it.
- Native Git processes can hang or emit sensitive remote data; context cancellation, sanitized
  arguments, environment allowlists, output caps, and no shell invocation are mandatory.

## Implementation Notes

Never construct a shell command string. Pass an explicit argument vector to `exec.CommandContext`,
disable credential helpers, and redact repository credentials from remotes and errors.
