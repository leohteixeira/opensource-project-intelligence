# ADR-016: Collect Only Public Source Data Using Operator-Managed Read Credentials

## Status

Accepted

## Date

2026-08-20

## Context

The product is intended for public open source intelligence and must not become a private
source-code analytics platform. At the same time, official APIs commonly provide higher quotas or
require authentication even when every requested resource is public. Treating public data and
anonymous API access as the same constraint would make collection unreliable on a publicly reachable
VPS.

## Decision

The product will collect only public repositories, packages, advisories, documentation, websites,
feeds, discussions, and related public metadata. It will never use a credential to expand visibility
into a private resource.

The VPS operator may configure shared, server-side, least-privilege read credentials to authenticate
official source requests and obtain usable quotas. End users do not provide, select, or view source
credentials. Product Admins may see redacted provider status and effective public-data capability,
but secret lifecycle remains an operator-managed boundary.

## Alternatives Considered

### Alternative 1: Anonymous Source Requests Only

- **Description**: Forbid credentials even when accessing public resources.
- **Pros**: No source secrets to manage.
- **Cons**: Low quotas and provider authentication requirements can prevent reliable collection.
- **Why rejected**: Public-data scope does not require anonymous transport.

### Alternative 2: Per-User Source Credentials

- **Description**: Let users connect accounts to increase quotas.
- **Pros**: Distributes quota and credential ownership.
- **Cons**: Makes shared collection depend on personal accounts and risks accidental private access.
- **Why rejected**: Users selected a shared public-data service with operator-owned credentials.

## Consequences

### Positive

- The product has a clear public-intelligence boundary.
- Collection can use official authenticated quotas without exposing secrets to users.
- User removal cannot disable a provider integration.

### Negative

- The VPS operator must provision and rotate read credentials outside normal user workflows.
- Provider permission drift must be detected so a credential cannot silently broaden collection.

### Risks

- A mis-scoped credential could see private data; collection must reject non-public resources even
  if the provider returns them.
- Public status can change; previously collected content needs explicit handling when a source
  becomes private or disappears.

## Implementation Notes

Stage 2 will define the operator configuration surface, scope validation, redacted status, public
visibility checks, provider-specific quota reporting, and behavior when a public source is removed.
