# ADR-002: Treat the Complete Product Vision as One Delivery

## Status

Accepted

## Date

2026-08-20

## Context

The source proposal separates an initial MVP from V2 and V3 evolutions. The MVP validates a narrow
GitHub-based vertical slice, while later phases add issue intelligence, trends, alerts,
natural-language analysis, multiple providers, package registries, adoption signals, health scoring,
and early-warning capabilities. The specification workflow can describe the entire desired scope in
one contract, but the product could still expose those capabilities through separate release
milestones.

## Decision

The specification will define the complete product vision as one product delivery. The product is
not considered delivered until the capabilities described across the original MVP, V2, and V3 are
implemented and work together. Internal build order and verification checkpoints may reduce delivery
risk, but they do not create separately accepted product releases or remove later capabilities from
the completion contract.

## Alternatives Considered

### Alternative 1: One Specification With Incremental Product Deliveries

- **Description**: Keep all capabilities in scope but accept independently usable MVP, V2, and V3
  product releases.
- **Pros**: Earlier user feedback, smaller release risk, and a production validation point for the
  ingestion foundation.
- **Cons**: The delivered product could stop at the GitHub dashboard-like slice that the vision is
  intended to transcend.
- **Why rejected**: The user explicitly selected a single complete delivery.

### Alternative 2: Continuous Capability Delivery Without Milestones

- **Description**: Order work by dependencies and value without retaining the proposal's phase
  boundaries or a single completion gate.
- **Pros**: Maximum sequencing flexibility.
- **Cons**: Ambiguous product completeness and weaker accountability for the advanced intelligence
  capabilities.
- **Why rejected**: The selected direction requires the full vision to form one completion contract.

## Consequences

### Positive

- Product acceptance covers the intelligence layer rather than only ingestion and dashboards.
- Cross-capability behavior can be specified and tested as one coherent experience.
- Advanced capabilities cannot silently become indefinite follow-up work.

### Negative

- Users receive no accepted partial product release before the full scope is complete.
- Integration, test, and release risk accumulate across a large implementation surface.
- Internal sequencing must provide strong verification gates even though those gates are not
  separate product deliveries.

### Risks

- The implementation could become too broad to integrate safely; the technical design must define
  dependency-ordered internal slices with explicit verification gates.
- Teams may treat internal checkpoints as releasable MVPs despite this decision; tracking documents
  must distinguish implementation checkpoints from product acceptance.

## Implementation Notes

Stage 2 will define a dependency-ordered build sequence. The mandatory MVP Boundary section of the
technical spec will state that the complete numbered task set constitutes the accepted product and
that any narrower vertical slice is an internal implementation checkpoint only.
