# ADR-031: Build an Accessible Localized React SPA From Headless Primitives

## Status

Accepted; requires a repository ADR before dependency adoption

## Date

2026-08-21

## Context

The current React application is a static placeholder. The frozen surface requires localized routes,
protected navigation, server state, large paginated tables, forms, radar, charts, contributor
graphs, mobile detail, keyboard operation, and WCAG 2.2 AA behavior. A custom implementation of
every primitive would duplicate mature accessibility and state machinery.

## Decision

Use React Router 7 in Data Mode, TanStack Query v5, React Hook Form, Zod, and `react-i18next` with
ICU messages. URL state owns shareable filters and windows; TanStack Query owns server state;
component state owns transient interaction. Do not add a general global-state library without a
concrete case.

Use React Aria Components behind repository-local wrappers, CSS design tokens, and CSS Modules. Use
TanStack Table for server-driven table behavior and Apache ECharts for supplementary radar, time
series, and graphs. Every visualization has a semantically equivalent table or list as its primary
accessible representation.

English and Portuguese dictionaries are committed in feature namespaces. One typed route manifest
maps canonical route keys to `/en/...` and translated `/pt-br/...` segments. API routes, fields,
error codes, and metric identifiers remain stable English.

## Alternatives Considered

### Alternative 1: Custom hooks and primitives only

- **Description**: Build routing, cache, forms, validation, tables, and interactions locally.
- **Pros**: Minimal dependency list.
- **Cons**: Large correctness and accessibility burden unrelated to product intelligence.
- **Why rejected**: Headless libraries preserve local design ownership while reducing repeated work.

### Alternative 2: Fullstack React meta-framework

- **Description**: Replace Vite SPA architecture with an SSR/fullstack framework.
- **Pros**: Integrated routing and server rendering.
- **Cons**: Changes the accepted backend boundary and adds a second server application.
- **Why rejected**: Public discovery and protected intelligence do not require SSR for this
  delivery.

## Consequences

### Positive

- Server state, forms, localization, tables, and interaction semantics have explicit owners.
- UI remains visually repository-owned and testable without charts.

### Negative

- The frontend dependency surface expands materially.
- Local wrappers must prevent inconsistent direct library usage.

### Risks

- Route translations can diverge; manifest generation and round-trip tests make divergence fatal.
- Chart accessibility can regress; browser tests and manual WCAG review cover non-automatable cases.

## Implementation Notes

Create a repository ADR that supersedes the no-router/no-data-fetching phase clause of ADR 0006
before adding dependencies. Pin every version in `pnpm-lock.yaml`.
