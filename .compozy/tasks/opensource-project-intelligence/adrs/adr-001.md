# ADR-001: Require Application-Managed Access Control

## Status

Accepted

## Date

2026-08-20

## Context

The source proposal defines the initial product as a single trusted workspace without user
authentication, authorization, OAuth, or application-managed roles. That boundary allows a smaller
MVP, but it also means that anyone who can reach the application can register projects and change
the shared catalog. The product specification now covers the complete product vision rather than
only the original MVP, and its primary user is a technical leader or architect making
technology-adoption decisions. Those decisions and the collected intelligence require explicit
control over who can view, curate, and administer the product.

## Decision

The product will provide application-managed authentication and role-based authorization as part of
the planned product scope. Access to reading intelligence, curating tracked projects, managing data
sources and credentials, and administering users will be governed by explicit permissions rather
than only by a trusted network perimeter.

The product grill will define the workspace and role semantics. The technical authentication
mechanism, credential lifecycle, and enforcement design will be selected during Stage 2 after the
public product surface is frozen.

## Alternatives Considered

### Alternative 1: Trusted Internal Deployment Without Accounts

- **Description**: Rely on a private network boundary and allow every reachable user to view and
  mutate the shared catalog.
- **Pros**: Smallest implementation surface and alignment with the proposal's original MVP.
- **Cons**: No user accountability, no permission separation, and unsafe exposure beyond a tightly
  controlled network.
- **Why rejected**: The user explicitly selected application-managed authentication and roles.

### Alternative 2: Public Read Access With Operator-Only Mutation

- **Description**: Let anyone view intelligence while project mutations remain on a separately
  protected operational surface.
- **Pros**: Supports public discovery without implementing a complete end-user role model.
- **Cons**: Splits the product experience and does not support controlled access to potentially
  organization-specific project portfolios or analyses.
- **Why rejected**: The selected direction requires authentication and authorization within the
  application itself.

## Consequences

### Positive

- The product can distinguish readers, project curators, and integration administrators.
- Project portfolios and derived analyses can be exposed only to authorized users.
- Mutating actions can be attributed to an authenticated identity.

### Negative

- User, session, invitation, and authorization lifecycles become part of the product and test scope.
- Every web and HTTP surface must define and enforce access behavior.
- Deployment requires a secure identity and session configuration rather than only a network
  perimeter.

### Risks

- A vague role model could create inconsistent permissions; the product grill must settle roles and
  workspace boundaries before Part I is written.
- A provider-specific authentication design could reduce deployability; Stage 2 must preserve the
  cloud-agnostic constraint and record the selected mechanism.

## Implementation Notes

No authentication technology is selected by this ADR. Stage 2 will define concrete interfaces,
storage, session security, bootstrap administration, and API enforcement after the user confirms the
product-level workspace and role behavior.
