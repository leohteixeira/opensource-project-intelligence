# ADR-028: Keep Identity External and Authorization and Sessions Local

## Status

Accepted

## Date

2026-08-21

## Context

One shared Keycloak will serve the three workspace products, while this product has one local
workspace, pending membership, fixed roles, service-account scopes, immediate suspension, and audit
requirements. Mirroring Keycloak groups directly would couple product policy to a global identity
deployment. Stateless sessions would delay local revocation.

## Decision

Use standards-based OIDC Authorization Code with PKCE through `go-oidc` and `x/oauth2`. Issuer,
audience, redirect origins, and JWKS discovery come from external configuration. The Keycloak `sub`
is the stable external identity; this repository never calls the Keycloak Admin API.

PostgreSQL owns pending membership, local role, status, service-account approval, scope subset, and
audit. Browser sessions are opaque random tokens in Secure, HttpOnly, SameSite=Lax cookies. Only a
token hash is stored. Login, privilege change, and reauthentication rotate the token. Suspension,
role change, service-account revocation, and account deletion revoke applicable sessions before the
state change is reported complete.

Automation presents Keycloak bearer tokens. Authentication validates issuer, audience, signature,
time claims, and subject; authorization then loads the approved local service account and intersects
its fixed Viewer/Analyst role with its local scopes. Service accounts can never receive Admin.

## Alternatives Considered

### Alternative 1: Keycloak roles are product roles

- **Description**: Trust realm groups or client roles directly for every authorization decision.
- **Pros**: Less local authorization state.
- **Cons**: Couples global identity governance to product policy and approval workflows.
- **Why rejected**: The user explicitly placed product authorization inside this repository.

### Alternative 2: Encrypted stateless browser cookies

- **Description**: Store all session state in a signed and encrypted browser cookie.
- **Pros**: No session lookup.
- **Cons**: Immediate suspension and role revocation require additional revocation machinery.
- **Why rejected**: Local state already requires a database check and immediate revocation matters.

## Consequences

### Positive

- Shared Keycloak remains independently governed.
- Product access changes take effect on the next request and are auditable.
- Browser and automation authentication converge on the same local authorization engine.

### Negative

- Protected requests perform local membership/session checks.
- Keycloak and local subject lifecycle require reconciliation diagnostics.

### Risks

- Claim-contract drift can block login; readiness exposes redacted OIDC validation status.
- Stolen bearer tokens remain valid until Keycloak expiry or local revocation; scopes and short
  token lifetimes reduce exposure.

## Implementation Notes

Do not persist access, refresh, or ID tokens unless a standards flow strictly requires it; if a
refresh token is introduced, encrypt it outside ordinary query output and treat it as a secret.
