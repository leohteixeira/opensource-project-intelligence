# ADR-034: Contain Google ADK Go v2 Behind Analysis Ports

## Status

Accepted; requires a repository ADR before dependency adoption

## Date

2026-08-21

## Context

The product includes single-shot structured analyses, embeddings, reranking, multi-tool natural
language analysis, and human-approved agent actions. Routing every model call through an agent
runtime would make simple deterministic pipelines harder to test. Avoiding a framework entirely
would duplicate graph, tool, pause, and resume mechanics the selected Google ADK provides.

## Decision

Use Google ADK for Go v2 only for genuinely agentic flows: natural-language analytics, multi-tool
analysis, graph workflows, and HITL pause/resume. ADK agents receive allowlisted function tools that
call application services through narrow interfaces. They never receive database, NATS, Valkey,
object-storage, provider SDK, or unrestricted HTTP access.

Single-shot release analysis, embedding, reranking, topic labeling, and evidence summarization
remain ordinary application services. Capability ports for structured generation, embeddings, and
reranking are owned by consumers. The initial model adapter uses an OpenAI-compatible HTTP contract;
provider-specific adapters may be added behind the same ports.

PostgreSQL remains authoritative for AnalysisRun, prompt version, tool call, evidence, token usage,
cost, status, approval, and result. An ADK session adapter maps runtime events into these canonical
records. ADK types do not leave `internal/analysis/agent` and do not define public API models.

## Alternatives Considered

### Alternative 1: Custom agent executor

- **Description**: Implement graph orchestration, tools, HITL, and sessions directly.
- **Pros**: Smallest dependency boundary.
- **Cons**: Rebuilds substantial agent-runtime behavior and its failure modes.
- **Why rejected**: The user selected Google ADK Go for the advanced orchestration surface.

### Alternative 2: Route all AI through ADK

- **Description**: Use agents for embeddings, reranking, and every structured generation call.
- **Pros**: One invocation API.
- **Cons**: Makes simple operations depend on agent session and event semantics.
- **Why rejected**: Ports by model capability are clearer and degrade independently.

## Consequences

### Positive

- Agentic flows gain graph, tool, and HITL mechanics without controlling the domain.
- Simple AI pipelines remain deterministic around one structured provider call.

### Negative

- Two orchestration paths exist: application services and ADK workflows.
- ADK upgrades require adapter and conformance testing.

### Risks

- Tool proliferation can expand authority; every tool is allowlisted, input-validated, scoped to the
  current actor, and capped by steps, duration, tokens, cost, and output bytes.
- ADK session semantics may change across major versions; pin v2 and persist canonical events first.

## Implementation Notes

Use ADK's graph workflow and HITL primitives but not its standalone API server as the product API.
The existing Go API and worker remain the only product processes unless a later ADR proves a need.
