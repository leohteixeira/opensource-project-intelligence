# ADR-013: Purge Deleted Project Data and Retain a Minimal Audit Tombstone

## Status

Accepted

## Date

2026-08-20

## Context

Projects can be paused or archived when users want to stop synchronization or remove them from
active views. Permanent deletion therefore needs a meaning distinct from those reversible states.
Removing every trace would make an administrative destructive action unauditable, while retaining
all collected content would make deletion equivalent to another soft-delete state.

## Decision

After an Admin explicitly confirms permanent deletion, the product will cancel the Project's pending
work and purge its raw payloads, canonical data, metric snapshots, analyses, associations, alerts,
and generated exports. The operation will preserve only a minimal audit tombstone containing the
opaque deleted Project identifier, actor, time, and deletion outcome. The tombstone will contain no
collected source content.

Deletion is not available to Analysts, Viewers, or the HITL assistant. Paused and archived Projects
must be used whenever retention is desired.

## Alternatives Considered

### Alternative 1: Indefinite Soft Delete

- **Description**: Hide the Project while retaining all data.
- **Pros**: Easy recovery and continued audit access.
- **Cons**: Does not provide meaningful permanent deletion and duplicates the archive lifecycle.
- **Why rejected**: The selected lifecycle already provides reversible archive behavior.

### Alternative 2: Remove Every Trace

- **Description**: Purge Project data and the fact that deletion occurred.
- **Pros**: Minimum retained state.
- **Cons**: Destructive administration becomes impossible to attribute or investigate.
- **Why rejected**: A payload-free tombstone provides accountability without retaining the Project.

## Consequences

### Positive

- Permanent deletion has predictable data-removal semantics.
- Archive remains clearly distinct as the recoverable state.
- Administrators can prove that a deletion occurred without retaining collected content.

### Negative

- Deleted Project intelligence cannot be restored without registering and collecting it again.
- References from audit or external exports may point to an opaque deleted identifier.

### Risks

- Partial purge could leave derived data behind; Stage 2 must define transactional or resumable
  deletion and verification.
- In-flight jobs could recreate data after deletion; cancellation and write guards must be part of
  the deletion invariant.

## Implementation Notes

Stage 2 will enumerate every owned record, define purge ordering and retries, specify confirmation
copy, and test deletion against in-flight collection and analysis.
