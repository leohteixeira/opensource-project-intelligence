# ADR-021: Localize Browser Routes and Keep the API Stable in English

## Status

Accepted

## Date

2026-08-21

## Context

The complete browser experience is bilingual in English and Brazilian Portuguese. Shared links must
open in their intended language, while API automation needs one language-independent contract.

## Decision

Use localized browser paths under `/en` and `/pt-br`, including translated Portuguese path segments.
Changing locale maps the current resource and query state to its equivalent path. Keep `/api/v1`,
JSON fields, metric names, states, and error codes stable in English. Localize fixed human-facing
response text through `Accept-Language`.

## Alternatives Considered

### Alternative 1: English routes for both locales

- **Description**: Translate labels only.
- **Pros**: One browser route table.
- **Cons**: Does not provide the selected localized URL experience.
- **Why rejected**: Browser routes were explicitly selected for localization.

### Alternative 2: Localize the API contract

- **Description**: Translate API paths, fields, or codes.
- **Pros**: Fully localized technical representation.
- **Cons**: Fragments automation, caching, documentation, and compatibility.
- **Why rejected**: Technical names must remain stable across locales.

## Consequences

### Positive

- Shared browser links express their language explicitly.
- Automation has one stable contract.

### Negative

- Browser navigation must maintain two route dictionaries and equivalent deep links.
- Every route addition requires English and Portuguese path coverage.

### Risks

- Locale switching could lose filters or route context; equivalence tests must cover every route.

## Implementation Notes

The root selects a supported locale and redirects. Pages expose canonical and `hreflang` links.
