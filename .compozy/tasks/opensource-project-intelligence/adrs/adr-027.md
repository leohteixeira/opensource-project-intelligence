# ADR-027: Generate HTTP and SQL Boundaries From Reviewed Contracts

## Status

Accepted; requires repository ADRs before implementation

## Date

2026-08-21

## Context

The frozen HTTP surface is large enough that hand-maintained Go DTOs, TypeScript DTOs, examples, and
documentation would drift. The complete persistence design also exceeds the roughly thirty-query
reassessment trigger in repository ADR 0003. Generated code must not hide business rules, metric
SQL, authorization, or transaction boundaries.

## Decision

A committed OpenAPI 3.1 document is the HTTP contract source of truth. A pinned `oapi-codegen`
version generates `net/http` strict-server types and a TypeScript client. Hand-written middleware
and application services enforce authentication, authorization, idempotency, ETags, validation,
transactions, and domain errors.

A pinned `sqlc` version generates typed query adapters for `pgx/v5`. SQL remains committed,
reviewable, and explicit. Generated records stay inside `internal/platform/database` and repository
adapters; business ports use canonical domain types. Versioned SQL migrations continue through the
existing migration runner.

Repository ADR 0003 remains historical. Before the first generated query lands, a new repository ADR
must supersede only its no-query-generator clause and update repository instructions. Its `pgx/v5`,
explicit SQL, manual migration, redaction, and transaction decisions remain in force.

## Alternatives Considered

### Alternative 1: Hand-maintain every contract

- **Description**: Write server DTOs, web DTOs, SQL scanning, and documentation independently.
- **Pros**: No generation tools.
- **Cons**: Repeats a large contract and preserves recurring mapping risk.
- **Why rejected**: The generated boundaries have stable authoritative inputs and clear ownership.

### Alternative 2: Adopt an ORM and HTTP framework

- **Description**: Derive schemas and routes from framework models.
- **Pros**: Less explicit adapter code.
- **Cons**: Conflicts with accepted `net/http`, explicit SQL, and auditability decisions.
- **Why rejected**: Generation should remove duplication, not relocate business ownership.

## Consequences

### Positive

- API examples, Go types, and TypeScript clients can be checked for drift.
- SQL types and nullable columns are compile-time visible without an ORM.

### Negative

- Tool versions and generated output become build inputs.
- Contract changes require intentional regeneration and review.

### Risks

- Developers may put business logic in generated layers; package boundaries and tests prohibit it.
- OpenAPI cannot express every authorization rule; the spec and application tests remain required.

## Implementation Notes

Generated files carry headers and are never edited manually. CI regenerates into a temporary
directory and fails on diff. OpenAPI examples must remain identical to `_dx.md` examples.
