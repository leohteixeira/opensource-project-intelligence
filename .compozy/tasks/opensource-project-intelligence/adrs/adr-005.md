# ADR-005: Keep Projects Independent From Their Typed Repositories

## Status

Accepted

## Date

2026-08-20

## Context

The product evaluates technologies rather than isolated source repositories. A technology may split
its implementation, documentation, examples, and SDKs across multiple repositories, while a user
still needs a low-friction way to begin tracking a project from the repository URL they already
know. Collapsing the two concepts would make multi-repository intelligence and later source
expansion ambiguous.

## Decision

`Project` and `Repository` will remain distinct product concepts. A project owns one or more
repositories, and every repository has an explicit product-defined type such as primary, docs,
examples, or SDK. A project must have one primary repository at creation time; additional typed
repositories may be attached later.

The quick-registration journey accepts a supported repository URL and creates both the project and
its primary repository. Users can review and edit the generated project identity before or after
initial synchronization. Metrics and analyses must state whether they apply to one repository or to
the aggregated project.

## Alternatives Considered

### Alternative 1: One Repository Per Project

- **Description**: Treat a registered repository as the project itself.
- **Pros**: Simplest registration and aggregation model.
- **Cons**: Produces incomplete intelligence for projects whose activity is distributed across
  implementation, docs, SDK, and example repositories.
- **Why rejected**: It violates the product's explicit `Project != Repository` invariant.

### Alternative 2: Owner or Organization as Project

- **Description**: Automatically treat every repository under a source owner as one project.
- **Pros**: Captures broad ecosystems with little manual setup.
- **Cons**: Source ownership does not reliably represent one product and would pull unrelated
  repositories into metrics.
- **Why rejected**: Users need an explicit, curated project boundary independent of vendor models.

## Consequences

### Positive

- Project intelligence can represent real multi-repository technologies.
- Repository roles make aggregation and evidence provenance understandable.
- Quick registration preserves a simple golden path.

### Negative

- Registration, synchronization, metrics, and comparisons must handle aggregation boundaries.
- Users may need to correct inferred project names or repository roles.

### Risks

- Double-counting contributors or cross-repository activity could distort project metrics; each
  metric must define its aggregation and deduplication rules.
- A missing or incorrectly typed repository can make project intelligence incomplete; the product
  must expose source coverage and freshness.

## Implementation Notes

Stage 2 will define repository role identifiers, source-neutral canonical IDs, aggregation rules,
and the URL-resolution contract for every supported repository provider.
